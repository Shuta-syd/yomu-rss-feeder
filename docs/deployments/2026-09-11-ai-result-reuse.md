# AI result reuse (2026-09-11)

Purpose: avoid paying repeatedly when multiple feeds provide identical AI inputs for the same original article. Article records, read/favorite states and feed listings remain independent.

Reuse requires the same normalized HTTP(S) URL, exact system/user prompts, provider, model, purpose, temperature and output cap. URL normalization is shared with display grouping, removing fragments and known tracking parameters while retaining content-bearing parameters, paths and schemes. Headline similarity is never sufficient. Different source text, titles, HTML, model, or summary lens causes a separate generation; this intentionally means not every visually grouped article can reuse a result. Classification-only and summary/classification have different prompts and remain separate.

Stage 1 and streamed stage 2 use a persistent SQLite ai_result_cache table (migration 0013). Only schema-validated responses are stored, for 30 days. Identical in-flight requests coordinate using a transactional owner lease across app and worker processes. Upstream generation runs outside transactions. Leases expire after five minutes, exceeding existing provider timeouts; a late owner cannot overwrite a replacement. Failures release their lease, malformed stored content is replaced, and stage-1 wait timeouts return the article to pending. Expired rows are pruned on cache access. Cache hits bypass the metered provider call and do not create fictitious paid usage records. reuse_count is internal operational evidence, not yet a settings UI metric.

Explicit stage-1 forceSummary and regeneration of completed stage-2 articles request a fresh result. Stage-2 cache hits preserve SSE chunk/done events and sanitize Markdown translation through the same existing path. Existing article results without a request fingerprint are not backfilled or regenerated. Savings accumulate from newly processed duplicates.
